# 独立可测试的案例库 API 设计

## 背景与目标

GitHub Issue #2 要求在不启动完整生产服务的情况下，测试能够启动生产线平衡改善案例库 API，并使用隔离的数据与文件存储验证 HTTP 契约和案例持久化状态。现有生产启动方式必须继续工作，内部员工现有的免登录阅读行为也不得改变。

## 方案

将 Express 应用组装从生产服务器启动逻辑中分离。

- 导出 `createApp(options)` 作为 API 的公共创建入口。
- `options` 提供 `dataDir` 与 `uploadsDir`；由此推导案例 JSON、认证 JSON、PPT 和预览目录。未提供时使用现有生产目录。
- 应用创建期间只组装中间件和路由；不得监听端口、生成样例案例或变更既有存储。
- 保留 `startServer()` 作为生产入口：它使用默认目录，运行现有样例数据与预览补全，再挂载 Vite 开发服务或生产静态资源并监听端口。

## 接口与行为

测试和未来调用方通过 `createApp({ dataDir, uploadsDir })` 得到一个 Express 应用。它们可以将该应用绑定到临时 HTTP server，并通过 HTTP 请求观察 API 行为。

文件与 JSON 数据只能落入传入的隔离目录。测试不读取路由内部状态、不调用私有辅助函数，也不触碰仓库的 `data/` 或 `uploads/`。

现有 API 路由、读者响应和下载计数语义保持不变。

## 验证

添加 Node 原生 HTTP 集成测试，不引入新的测试框架。每个测试创建独立临时目录，准备最小案例数据，启动 `createApp` 返回的应用，并断言：

1. 健康检查可通过 HTTP 调用。
2. 读者可通过 HTTP 获取案例列表。
3. 下载计数的 HTTP 操作成功后，临时 `ppts.json` 中的案例状态已递增。

最后运行 TypeScript 检查和完整测试脚本。生产启动命令也必须继续指向保留的 `startServer()`。

## 范围边界

不在本次工作中改变 SSO、角色权限、企业网络边界、案例字段、文件解析流程或前端行为；不引入数据库、依赖注入框架或外部测试框架。
